## 2. Bootstrap 同步的风险

### 当前 bootstrap 模式行为

当 Base 无 `clean_status` 字段时，VPS 脚本以 `--bootstrap-missing-clean-status` 模式运行：
- 允许同步**无** clean_status 的记录
- 在 metadata 中标记 `audit_warnings: ["missing_clean_status_bootstrap"]`
- 仍然要求**标题非空**、**正文非空**

### 风险清单

| # | 风险 | 严重程度 | 影响 |
|---|------|---------|------|
| B-01 | 无法区分正式清洗稿和草稿 | 🔴 高 | 草稿/半成品可能混入生产 corpus |
| B-02 | 拒绝稿、废弃稿无法排除 | 🔴 高 | 低质量语料污染 RAG 风格学习 |
| B-03 | 没有清洗时间追溯 | 🟡 中 | 无法判断语料新鲜度 |
| B-04 | source_type 全靠启发式推断 | 🟡 中 | "电广传媒917" 推断为 manual 而非 weekly_siqing |
| B-05 | 无法标记需人工复核记录 | 🟡 中 | 问题语料无法在 Base 侧标识 |
| B-06 | bootstrap 模式本身是临时方案 | 🟠 低-中 | 长期使用会形成路径依赖 |

### 结论

**Bootstrap 模式不可作为长期生产默认。** 仅适用于：
1. 旧表迁移过渡期
2. 测试/开发环境验证
3. 一次性历史数据抢救

## 5. Strict Cleaned-Only 生产准入规则

### 核心原则

> **生产正式同步必须使用 strict-cleaned-only 模式。**

### 准入条件（必须全部满足）

| # | 条件 | 不满足时行为 |
|---|------|-------------|
| 1 | `clean_status` 字段存在 | ❌ 跳过（strict 硬阻塞） |
| 2 | `clean_status` == `"cleaned"` | ❌ 跳过 |
| 3 | 标题非空 | ❌ 跳过 |
| 4 | 正文非空 | ❌ 跳过 |
| 5 | `rag_usage` = `"style_only"` | ❌ 跳过（VPS 侧固定） |
| 6 | `is_fact_safe` = `false` | ❌ 跳过（VPS 侧固定） |

### 处理规则

| clean_status | needs_manual_review | VPS 行为 | audit_status |
|-------------|--------------------|---------|-------------|
| `cleaned` | false | ✅ 正常同步 | `passed` |
| `cleaned` | true | ✅ 同步（落盘为 review_required） | `review_required` |
| `cleaned` | true + reason | ✅ 同步 | `review_required` |
| `needs_review` | — | ❌ 跳过 | 不入 corpus |
| `raw` | — | ❌ 跳过 | 不入 corpus |
| `rejected` | — | ❌ 跳过 | 不入 corpus |
| *(缺失)* | — | ❌ 跳过（strict 硬阻塞） | 不入 corpus |

### 需要人工复核的记录

- **可以落盘到 VPS corpus**，metadata 标记为 `audit_status: "review_required"`
- **不建议进入后续 Qdrant ingest**，除非人工复核后将 `is_fact_safe` 改为 `true` 或人工确认安全
- Qdrant ingest 脚本（Stage C）应过滤 `audit_status != "passed"` 的记录

### 不可同步的记录

- 正文为空 → **硬阻塞**，不同步
- 标题为空 → **硬阻塞**，不同步
- clean_status 不等于 `cleaned` → **跳过**
- clean_status 缺失 → **跳过**（strict 模式）

## 6. Bootstrap 模式边界

### 允许使用 Bootstrap 的场景

1. **旧表一次性迁移**: Base 尚未添加 clean_status 字段时，用 bootstrap 做一次性历史数据落盘
2. **测试/开发**: fixture 测试、本地开发验证
3. **紧急数据抢救**: 特殊情况需快速获取数据时

### 禁止使用 Bootstrap 的场景

1. ❌ **日常生产同步**: 不作为定期生产默认模式
2. ❌ **新增语料同步**: Base 已有 clean_status 后，新语料必须通过 strict 模式
3. ❌ **全量正式落盘**: 正式 corpus 落盘必须 strict

### Bootstrap 退出条件

当满足以下条件时，应关闭 bootstrap 模式：
1. Base 已添加 `clean_status` 字段
2. 所有已有记录已标记 clean_status（至少已区分 cleaned / raw / rejected）
3. VPS 侧 strict 模式 dry-run 无 fatal error

## 7. 首次正式落盘策略

### 前置条件（全部满足才启动）

- [ ] Base 已添加 clean_status 单选字段（options: cleaned / raw / needs_review / rejected）
- [ ] 所有已有 Base 记录已标记 clean_status
- [ ] Base 已添加 source_type 字段（或 VPS 已验证启发式推断精度可接受）
- [ ] VPS strict 模式 dry-run (limit 5) 全部通过
- [ ] VPS strict 模式 dry-run (全量) 全部通过，ERROR = 0
- [ ] audit_manifest.py 全量审计 PASS（ERROR = 0）

### 首次落盘流程

```
Step 1: strict dry-run 全量预检
  └─ sync_from_lark_base.py --strict-cleaned-only --dry-run --limit 0
  └─ 确认无 fatal error

Step 2: strict 同步到临时目录
  └─ sync_from_lark_base.py --strict-cleaned-only --output-root /tmp/corpus-staging --limit 0
  └─ 输出统计：Processed / Skipped / Warnings

Step 3: 临时目录审计
  └─ audit_manifest.py --manifest /tmp/corpus-staging/manifests/manifest-v0.2.0.jsonl --corpus-root /tmp/corpus-staging --fail-on-error
  └─ 必须全部 PASS

Step 4: 复制到正式 corpus 目录
  └─ rsync /tmp/corpus-staging/ → corpus/mango_style_docs/
  └─ 不覆盖已有 cleaned/*.md（增量追加）

Step 5: 正式 corpus 审计
  └─ audit_manifest.py 对正式目录再次审计
  └─ 必须全部 PASS

Step 6: manifest snapshot
  └─ 复制 manifest-v0.2.0.jsonl → manifests/manifest-v0.2.0-first-sync.jsonl
  └─ 归档首次同步快照
```

## 8. 回滚和重跑策略

### 回滚方案

1. **manifest snapshot**: 每次同步后保存 manifest 副本（带时间戳）
2. **corpus 清空**: 如需回滚，删除 `corpus/mango_style_docs/cleaned/`、`metadata/`、`manifests/` 中所有 v0.2.0 产物
3. **从 snapshot 恢复**: `cp manifests/manifest-v0.2.0-{timestamp}.jsonl manifests/manifest-v0.2.0.jsonl`，然后仅保留 manifest 中列出的文件

### 重跑策略

- **幂等设计**: 同一 record_id 同步两次，doc_id 相同，文件内容相同（content_hash 校验）
- **增量追加**: 新同步只新增 doc_id，不覆盖已有文件（除非 content_hash 不匹配时发出警告）
- **全量重跑**: 删除所有 v0.2.0 产物，从 manifest snapshot 重新同步（等价于 fresh start）

### 风险控制

| 操作 | 可逆性 | 建议 |
|------|--------|------|
| 删除 corpus 产物 | ✅ 可逆（从 manifest snapshot 恢复） | 建议先备份 manifest |
| 覆盖已有 metadata | ⚠️ 部分可逆 | 不建议覆盖，用增量追加 |
| 修改 VPS 脚本 | ✅ git revert | 提交 git commit 后可回退 |

## 11. 是否建议先让飞书 OpenClaw 补 Base 字段

**✅ 强烈建议。**

### 理由

1. **strict 模式依赖 clean_status**: 没有 clean_status，VPS 只能用 bootstrap，无法做正式生产同步
2. **source_type 提升精度**: 启发式推断无法区分 "电广传媒917" 和真正的司情
3. **审计完整性**: needs_manual_review + manual_review_reason 让 Base 侧能标记问题记录
4. **追溯能力**: cleaner + cleaned_at 让每条记录有清洗操作记录

### 建议执行顺序

1. 飞书 OpenClaw 在 Base 新增 Phase 1 最小必需字段（9 个）
2. 飞书 OpenClaw 遍历已有记录，回填 clean_status（至少区分 cleaned / raw / rejected）
3. 飞书 OpenClaw 遍历已有记录，回填 source_type（启发式 + 人工确认）
4. VPS 用 strict 模式 dry-run 验证
5. 全部 PASS 后启动 Stage B1

### 风险

- 飞书 OpenClaw 回填 clean_status 需要人工确认，不能完全自动化
- source_type 启发式推断可能有误差，建议人工复核 "电广传媒917" 等模糊来源
