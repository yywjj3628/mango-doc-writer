## 一、审计结果

### 1.1 模型配置位置

| 配置项 | 位置 | 默认值 |
|--------|------|--------|
| 主模型 | `.env` → `DEEPSEEK_MODEL` | deepseek-v4-flash |
| 备用模型 | `.env` → `DEEPSEEK_FALLBACK_MODEL` | deepseek-v4-pro |
| 读取位置 | `pipeline/model_client.py:110` | `os.getenv("DEEPSEEK_MODEL")` |
| 调用方式 | 每次 API 调用时读取 env var | 不是启动时缓存 |

### 1.2 是否支持临时模型切换

**✅ 支持，无需改代码。**

`model_client.py` 在每次调用时读取 `os.getenv("DEEPSEEK_MODEL")`，而 `run_gray.py` 使用 `subprocess.run` 继承父进程环境。因此：

```bash
DEEPSEEK_MODEL=deepseek-v4-pro python3 scripts/run_gray.py ...
```

即可临时切换模型，不影响 .env 和 production。

### 1.3 当前 04-draft prompt 篇幅约束状态

| 约束点 | 是否存在 | 说明 |
|--------|---------|------|
| `{{requirement}}` 注入 | ✅ | requirement 中包含字数目标 |
| `total_word_count_estimate` 遵守 | ⚠️ 有提及 | prompt 说"必须逐条遵守"，但模型当建议 |
| "正文不得低于 X 字"硬约束 | ❌ 无 | 没有任何硬性字数下限 |
| rewrite 不得压缩 | ❌ 无 | rewrite 阶段可能压缩内容 |

### 1.4 长文偏短原因排序

| 原因 | 可能性 | 说明 |
|------|--------|------|
| 1. prompt 无硬性字数下限 | **高** | 04-draft 只说"遵守 total_word_count_estimate"，没有"不得少于 X 字" |
| 2. flash 模型倾向简洁 | **中高** | DeepSeek v4-flash 偏好精炼输出，长文能力弱于 pro |
| 3. rewrite 阶段压缩 | **中** | review/rewrite 可能删除"多余"内容 |
| 4. plan 阶段 estimate 偏低 | **低** | plan 的 total_word_count_estimate 可能没有反映 requirement 中的目标 |

## 二、flash vs pro 对比验证

### 2.1 Test Case：芒果公众号宣传推文

素材："6月4日，电广传媒参与青春芒果派相关活动…"

| 指标 | flash (C1.13C.1) | pro |
|------|-----------------|-----|
| Pipeline | success (150s) | **❌ 超时 (600s)** |
| actual_word_count | 372 | N/A |
| QG | pass | N/A |

**pro 超时原因分析**：
- pro 模型推理速度显著慢于 flash
- 6 阶段 pipeline + 质量返修循环，每阶段调用 1 次 pro
- 最多 10+ 次 pro 调用 × 平均 60-120s/次 = 600-1200s
- 600s timeout 不够

### 2.2 结论

**pro 模型在当前 pipeline 架构下不可行**，除非：
1. timeout 提高到 1200s+
2. 减少 pipeline 阶段数
3. 只在 draft 阶段用 pro，其他阶段用 flash

## 三、长文偏短根因定位

### 排除法

| 假设 | 验证结果 | 排除？ |
|------|---------|--------|
| requirement 没写目标字数 | C1.13C 已写入 | ❌ 不是这个原因 |
| plan 没读 requirement | plan 读取了 requirement | ❌ 不是这个原因 |
| draft 没读 plan 的 estimate | draft 读取了 draft_directives | ❌ 不是这个原因 |
| draft prompt 没强调字数下限 | 只说"遵守"，没有"不得少于" | ✅ **这是主因** |
| flash 模型能力不足 | pro 超时无法验证，但 flash 确实偏短 | ✅ **可能是辅因** |
| rewrite 压缩 | 可能存在，但未验证 | ⚠️ 待确认 |

### 核心结论

**主因是 04-draft prompt 没有硬性字数下限约束。** 模型把 requirement 中的"目标 800-1200 字"当作参考信息，而不是硬约束。

**辅因是 flash 模型倾向简洁。** 即使加了 prompt 约束，flash 可能仍不如 pro 写得长。

## 四、建议

### 4.1 最小 prompt 修复（C1.13E 推荐）

在 04-draft prompt 中增加条件性篇幅约束：

```
当 requirement 或 draft_directives 中包含目标篇幅时：
- 正文字数应尽量达到目标下限
- 不得为凑字编造姓名、职务、数据、时间、地点
- 如果素材不足，应扩展结构、背景、意义和工作逻辑
- 如实无法达到目标字数，应在人工复核提示中说明
```

**改动范围**：仅 04-draft.md，约 5-10 行
**风险**：低，不影响 production 默认（只在有目标字数时生效）

### 4.2 run_gray.py 增加 --model（可选）

增加 `--model` 参数，允许灰度调用时临时切换模型：

```python
parser.add_argument("--model", default=None, help="临时覆盖模型（默认使用 .env 配置）")
```

在 `set_gray_env()` 中：
```python
if args.model:
    os.environ["DEEPSEEK_MODEL"] = args.model
```

**改动范围**：run_gray.py，约 10 行
**风险**：低，只影响灰度调用

### 4.3 pro 模型可行性

**当前不可行**（超时），但可以通过以下方式解决：
1. 只在 draft 阶段用 pro，其他阶段用 flash
2. 或将 timeout 提高到 1200s+
3. 或减少质量返修轮次

**建议暂不使用 pro**，先验证 prompt 修复效果。

---

## 五、结论

### C. ⚠️ prompt 和模型都有影响，需要先做最小 prompt 修复，再做 pro 验证

**优先级**：
1. **P0**：04-draft prompt 增加条件性篇幅约束（5-10 行改动）
2. **P1**：run_gray.py 增加 `--model` 参数（10 行改动）
3. **P2**：flash vs pro 对比验证（需要先解决 pro 超时问题）

**不建议**：
- ❌ 不建议在当前架构下默认使用 pro（超时风险）
- ❌ 不建议大改 pipeline 架构
- ❌ 不建议在 prompt 中强制"必须达到 X 字"（可能导致编造）
