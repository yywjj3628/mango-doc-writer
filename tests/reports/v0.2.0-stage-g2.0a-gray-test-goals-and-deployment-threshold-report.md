## 二、灰度测试目标

### 核心定位

**真实灰度测试不是追求每篇一次成稿直接发布，而是验证系统是否能稳定作为"可人工修改后采用"的写作助手。**

即：系统输出的稿件，经人工少量修改后能用于实际工作，而不是从零开始写。

### 6 个核心能力验证

#### 1. 文种判断是否稳定

**解释**：系统能否根据用户输入素材和指定文种，输出正确文种结构的稿件。不把新闻稿写成汇报材料，不把会议新闻写成会议纪要。

**可观察指标**：
- classified_doc_type = requested_doc_type 的比例
- final_markdown 结构是否符合 doc-type-rules.md 中对应文种规则
- 是否出现严重文种误判（如会议新闻写成会议纪要）

#### 2. 主体/组织称谓是否不混

**解释**：系统能否正确区分不同主体，不把电广传媒和芒果超媒混用，不把子公司写成母公司，不把"公司"误指其他实体。

**可观察指标**：
- 输出中组织名称是否与输入素材一致
- 是否出现禁用称谓（如把久之润写成"公司"）
- 领导职务是否正确

#### 3. RAG 风格是否有效

**解释**：系统能否通过 RAG 检索到正确风格的参考语料，使输出符合指定 style_domain 的语调和表达习惯。

**可观察指标**：
- dianguang_siqing 是否克制正式
- mango_official_account 是否有传播感
- 两种风格是否有明显差异

#### 4. 规则库是否生效

**解释**：doc-type-rules.md 中的文种规则、org-title-dictionary.yaml 中的称谓规则是否被 pipeline 正确加载并影响输出。

**可观察指标**：
- 新增文种（亮点工作材料、宣传推文、工作方案、会议新闻）是否按规则输出
- 禁止事项是否被遵守（如不得编造数据、不得写成纪要口吻）
- 会议新闻 vs 会议纪要边界是否生效

#### 5. 输出是否能人工修改后采用

**解释**：系统输出的稿件质量是否达到"人工少量修改后可用于实际工作"的水平。不需要一次成稿完美，但修改量应可控。

**可观察指标**：
- 人工评价"直接采用"或"修改后采用"的比例
- 主要问题是否集中在可修复的范围内（如扩写不足、篇幅偏短）
- 是否存在不可修复的问题（如事实编造、主体混用）

#### 6. 事实风险是否可控

**解释**：系统输出是否出现事实编造、数据虚构、领导评价捏造等不可接受的风险。

**可观察指标**：
- 事实风险出现次数 = 0
- 是否有"需确认"标注（表明系统知道哪些信息需要人工核实）
- 扩写内容是否基于输入素材

## 三、评价维度（6 项）

每次灰度结果只评价 6 项，避免用户负担过重。

### 1. 文种：对 / 错

| 判断标准 | 值 |
|---------|-----|
| 对 | 输出文种 = 用户指定文种，或用户未指定时 classify 结果合理 |
| 错 | 输出文种与用户意图不符（如要新闻稿写成了汇报材料） |

### 2. 主体：对 / 错

| 判断标准 | 值 |
|---------|-----|
| 对 | 组织名称、领导职务与输入素材一致，未出现混用 |
| 错 | 出现主体混用（如电广传媒/芒果超媒混淆）、职务错误、禁用称谓 |

### 3. 事实：安全 / 有风险

| 判断标准 | 值 |
|---------|-----|
| 安全 | 输出内容基于输入素材，未编造数据/领导评价/获奖信息 |
| 有风险 | 出现编造事实、虚构数据、捏造领导评价 |

### 4. 风格：1-5 分

| 分数 | 含义 |
|------|------|
| 5 | 风格完全符合指定 style_domain，语调自然 |
| 4 | 风格基本符合，个别表达可优化 |
| 3 | 风格一般，有明显但不严重的偏差 |
| 2 | 风格偏差较大，需要较多调整 |
| 1 | 风格完全不对，需要重写 |

### 5. 可用性：直接采用 / 修改后采用 / 弃用

| 判断标准 | 值 |
|---------|-----|
| 直接采用 | 输出质量高，可直接用于实际工作 |
| 修改后采用 | 输出质量可接受，经少量修改（调整表达、补充细节）后可用于实际工作 |
| 弃用 | 输出质量差，修改量大于重写，或存在事实风险 |

### 6. 主要问题：一句话

简要描述本次输出的主要问题，如"扩写不足""篇幅偏短""风格偏差""主体混用"等。

## 四、部署前观察门槛

### 门槛清单

| # | 门槛 | 阈值 | 理由 |
|---|------|------|------|
| 1 | 累计灰度记录 | ≥ 20 篇 | 足够样本量判断系统稳定性 |
| 2 | 真实素材 | ≥ 8 篇 | 验证系统对真实工作素材的处理能力，非构造测试数据 |
| 3 | 文种覆盖 | ≥ 6 类 | 14 种文种中至少覆盖 6 种，验证多文种能力 |
| 4 | QG pass | ≥ 85% | 质量门禁通过率，允许个别低分但整体可控 |
| 5 | 人工"直接采用 + 修改后采用" | ≥ 80% | 核心指标：系统输出可人工修改后采用的比例 |
| 6 | 事实风险 | = 0 | 零容忍，任何事实编造必须修复后才能部署 |
| 7 | 主体混用 | = 0 | 零容忍，主体混淆必须修复后才能部署 |
| 8 | 严重文种误判 | ≤ 1 | 允许 1 次轻微误判，但严重误判（如纪要写成新闻）必须为 0 |

### 门槛合理性说明

- **20 篇累计**：覆盖主要文种和风格组合，统计意义足够
- **8 篇真实素材**：真实素材与构造素材差异大，必须验证
- **6 类文种**：14 种中覆盖 6 种（新闻稿、汇报材料、领导讲话、会议纪要、亮点工作材料、宣传推文），验证核心能力
- **85% QG**：允许 15% 低分，但整体质量可控
- **80% 采用率**：系统核心价值——"可人工修改后采用"
- **0 事实风险**：部署底线，不可妥协
- **0 主体混用**：部署底线，影响稿件可信度
- **≤1 文种误判**：允许少量学习空间，但严重误判必须修复

## 五、立即修复触发条件

以下问题出现后不能等 10 篇归类，必须立即修复：

| # | 触发条件 | 说明 | 修复方向 |
|---|---------|------|---------|
| 1 | 事实风险 | 编造数据、虚构领导评价、捏造获奖信息 | 检查 prompt 禁止事项、fact_safety_boundary |
| 2 | 主体混用 | 电广传媒/芒果超媒混淆、子公司写成母公司 | 检查 org-title-dictionary.yaml、classify prompt |
| 3 | 领导职务编造 | 编造不存在的职务、职务与实际不符 | 检查 org-title-dictionary.yaml leaders 部分 |
| 4 | 严重文种误判 | 会议新闻写成会议纪要、新闻稿写成汇报材料 | 检查 doc-type-rules.md、classify prompt |
| 5 | 禁用组织口径 | "公司"误指子公司、泛化组织名 | 检查 org-title-dictionary.yaml forbidden 称谓 |
| 6 | RAG 错库污染 | 错误 collection 的语料混入输出，风格完全不对 | 检查 rag_client.py routing table、DEFAULT_ROUTE |

### 修复流程

1. 问题发现 → 记录到灰度台账
2. 立即分析根因（规则库 / prompt / schema / 路由）
3. 最小修复 → 重新验证
4. 修复后补充 1 条验证灰度
