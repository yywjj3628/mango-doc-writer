## 三、五字段如何写入临时 JSON

临时 JSON 结构：
```json
{
  "requirement": "...",
  "draft": "素材文本",
  "generation_mode": "assisted_expansion",
  "specified_doc_type": "亮点工作材料",
  "style_domain": "dianguang_siqing",
  "organization_scope": "jiuzhirun",
  "content_type": "subsidiary_highlight",
  "length_mode": "standard"
}
```

**兼容策略**：output_doc_type 映射到 `specified_doc_type`（pipeline 现有字段），同时灰度记录中显示 `requested_output_doc_type`。

## 四、requirement 生成逻辑摘要

requirement 由 7 个部分拼接：

1. **扩写模式声明**：assisted_expansion / creative_mimic / 默认
2. **风格要求**：style_domain → "参考电广传媒司情风格…"
3. **组织主体**：organization_scope → "稿件主体为久之润/久游网…"
4. **内容题材**：content_type → "题材为子公司亮点工作…"
5. **输出文体**：output_doc_type → "最终成稿为亮点工作材料…"
6. **篇幅要求**：length_mode → "篇幅要求：800-1200字。"
7. **扩写规则**：assisted_expansion 模式下的扩写边界

## 九、发现的问题

### 问题 1：actual_word_count 偏低

3 个 test 的 actual_word_count 分别为 463/509/395 字，低于 standard 模式的目标（800-1200/700-1000/1000-1500）。

**原因**：requirement 中的篇幅要求写入了临时 JSON，但 pipeline 的 classify/extract/plan 阶段不读取这个字段，只有 draft 阶段的 prompt 中包含 requirement。模型可能没有充分遵循篇幅要求。

**建议**：C1.13C 需要在 prompt 层面强化篇幅控制。

### 问题 2：output_doc_type 与 classified_doc_type 不一致

- Test 1：requested=亮点工作材料, classified=汇报材料
- Test 2：requested=宣传推文, classified=新闻稿

**原因**：classify 阶段使用自己的枚举（不含亮点工作材料/宣传推文），且 specified_doc_type 只是 classify 的参考输入之一。

**影响**：不影响 RAG 路由（路由使用 classify 输出的 doc_type），但文种规则可能不匹配。

**建议**：后续考虑在 classify prompt 中支持更多文种枚举。
