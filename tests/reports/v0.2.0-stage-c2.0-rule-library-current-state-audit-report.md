## 二、Pipeline / Prompts 实际使用规则清单

### 2.1 Pipeline 加载机制

`pipeline/run_pipeline.py` 中 `_load_reference()` 函数从 `references/` 目录加载规则文件：

```python
# L108-112: 规则注入
if stage in ("plan", "draft", "review", "rewrite"):
    template_vars["doc_type_rules"] = _load_reference("doc-type-rules.md")
    template_vars["org_title_dictionary"] = _load_reference("org-title-dictionary.yaml")

if stage in ("draft", "review"):
    template_vars["style_rag_policy"] = _load_reference("style-rag-policy.md")
```

**注入方式：** 通过模板变量 `{{doc_type_rules}}`、`{{org_title_dictionary}}`、`{{style_rag_policy}}` 拼入 prompt。

## 四、五字段对应规则缺口

C1.13 新增的五字段在 pipeline 中已实现，但**没有对应的独立规则文件**：

| 字段 | 当前实现 | 独立规则文件 | 缺口评估 |
|------|---------|------------|---------|
| `style_domain` | run_gray.py `_STYLE_DOMAIN_HINTS` 硬编码 | ❌ 无 | **中等缺口** — hints 在脚本中，不在规则库 |
| `organization_scope` | run_gray.py `_ORG_SCOPE_HINTS` 硬编码 | ❌ 无 | **中等缺口** — hints 在脚本中，不在规则库 |
| `content_type` | run_gray.py `_CONTENT_TYPE_HINTS` 硬编码 | ❌ 无 | **中等缺口** — hints 在脚本中，不在规则库 |
| `output_doc_type` | doc-type-rules.md 部分覆盖 | ⚠️ 部分 | **小缺口** — 10 种文种有，但新增 3 种（亮点工作材料、宣传推文、工作方案）无 |
| `length_mode` | run_gray.py `_LENGTH_RULES` 硬编码 | ❌ 无 | **中等缺口** — 篇幅规则在脚本中，不在规则库 |

**关键问题：** 五字段的 hints 和 rules 目前硬编码在 `scripts/run_gray.py` 中，而非 `references/` 规则库。这意味着：
1. 规则修改需要改代码，而非改配置文件
2. 规则无法被其他脚本/工具复用
3. 规则无法通过人工审核流程管理

## 五、正式规则库与候选规则区边界建议

### 5.1 设计原则

```
正式规则库（references/rules/）
  ↓ 被 pipeline 直接读取
  ↓ 只包含人工确认的稳定规则
  ↓ 修改需要经过审核流程

候选规则区（tests/reports/rule-candidates/）
  ↓ 从语料中自动萃取
  ↓ 需要人工确认后才能进入正式规则库
  ↓ 可以包含未验证的候选规则
```

### 5.2 推荐目录结构

```
references/
├── doc-type-rules.md          # 现有，保留
├── org-title-dictionary.yaml  # 现有，保留
├── style-rag-policy.md        # 现有，保留
└── rules/                     # 新建，存放细分规则
    ├── organization.md        # 组织架构规则（从 org-title-dictionary.yaml 提取）
    ├── leader_titles.md       # 领导姓名职务规则（从 org-title-dictionary.yaml 提取）
    ├── subsidiaries.md        # 子公司归属规则（新建）
    ├── company_aliases.md     # 公司简称规则（新建）
    ├── style_domain_rules.md  # 风格域规则（从 run_gray.py 提取）
    ├── content_type_rules.md  # 内容题材规则（从 run_gray.py 提取）
    ├── expansion_policy.md    # 扩写边界规则（从 prompts 提取）
    └── risk_rules.md          # 事实安全规则（从 prompts 提取）

tests/reports/rule-candidates/  # 候选规则区
    ├── c2.2-leader-organization-candidates.jsonl
    ├── c2.3-human-review-template.md
    ├── c2.3-human-review-template.csv
    └── README.md              # 候选规则说明
```

### 5.3 边界判断

| 判断项 | 建议 |
|--------|------|
| 是否保留现有 references 文件？ | ✅ 保留原路径，不迁移 |
| 候选放在哪里？ | `tests/reports/rule-candidates/`（不在 references 下） |
| 现有规则是否需要迁移？ | 先保留原路径，后续逐步整理到 `references/rules/` |
| 哪些规则适合直接规则化？ | 组织架构、领导职务、公司简称、禁用称谓 |
| 哪些规则必须人工确认？ | 新语料萃取的规则、时效敏感信息、风险规则 |

## 七、自动萃取 vs 人工确认

### 7.1 可以自动萃取的规则

| 规则类型 | 萃取方法 | 置信度要求 |
|---------|---------|----------|
| leader_title | 从旧稿中提取高频出现的"姓名+职务"组合 | ≥ 3 篇旧稿出现 |
| organization | 从旧稿中提取组织名称和简称 | ≥ 5 篇旧稿出现 |
| company_alias | 从旧稿中提取公司简称使用场景 | ≥ 10 篇旧稿出现 |
| style_phrase | 从旧稿中提取高频表达模式 | ≥ 5 篇旧稿出现 |
| risk_rule | 从 prompts/05-review.md 中提取已有风险规则 | 直接提取 |

### 7.2 必须人工确认的规则

| 规则类型 | 原因 |
|---------|------|
| subsidiary | 子公司归属关系需要确认准确性 |
| doc_type_rule | 新文种规则需要确认结构和禁忌 |
| leader_title（时效敏感） | 领导职务变动需要确认 |
| organization（新发现） | 新出现的组织名称需要确认 |
| style_phrase（新风格） | 新风格表达需要确认是否合适 |
| risk_rule（新风险） | 新发现的风险点需要确认严重程度 |
