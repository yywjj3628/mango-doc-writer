## 三、expansion_report / expansion_review 未出现的原因

### 3.1 灰度记录检查逻辑 Bug ⚠️

gray-record 检查代码：
```python
has_expansion_report = "expansion_report" in report
has_expansion_review = "expansion_review" in report
```

但 pipeline_report.json 中的字段名是：
- `expansion_report_summary`（不是 `expansion_report`）
- `expansion_review_summary`（不是 `expansion_review`）

**结果**：gray-record 永远显示 ❌，即使数据实际存在于 `expansion_report_summary` / `expansion_review_summary` 中。

**这是 run_gray.py 的 Bug，不是 pipeline 的 Bug。**

### 3.2 模型未输出 expansion_report（根因）

draft.schema.json 中 `expansion_report` 是**可选字段**（不在 `required` 列表中），且 `additionalProperties: false`。

**但关键问题**：DeepSeek 模型（v4-flash）没有输出这些 v0.1.4 新增字段。可能原因：
1. 模型对长 prompt 中的新增指令注意力不足
2. schema 中这些字段是可选的，模型倾向于只输出 required 字段
3. prompt 中的示例 JSON 不够突出 expansion_report 结构

### 3.3 Pipeline fallback 已覆盖

run_pipeline.py 有完善的 fallback 逻辑：
- draft 阶段未输出 expansion_report → pipeline 自动补充（标记 missing: True）
- review 阶段未输出 expansion_review → pipeline 自动补充（标记 missing: True）
- creative_mimic 模式 draft_disclaimer 缺失 → 自动补充

**结论**：expansion_report / expansion_review 的数据**存在于 pipeline_report.json 中**（通过 fallback），但**来源是 pipeline 代码而非模型**。

## 四、assisted_expansion 输出差异不大的原因

### 4.1 根因：模型未真正执行扩写指令

审计发现以下链路断裂：

| 层级 | 是否传递 | 模型是否执行 |
|------|---------|------------|
| generation_mode 写入 JSON | ✅ | — |
| run_input 读取并传递 | ✅ | — |
| input_parser 保留 | ✅ | — |
| run_pipeline 注入 prompt | ✅ | — |
| 03-plan 要求 controlled_expansion_directives | ✅ | ❌ 模型未输出 |
| 04-draft 要求 expansion_report | ✅ | ❌ 模型未输出 |
| 05-review 要求 expansion_review | ✅ | ⚠️ 输出空壳 |
| 06-rewrite 保留可接受扩写 | ✅ | ⚠️ 无扩写可保留 |
| 07-quality-score 阈值下调 | ✅ | ✅ 生效 |

### 4.2 具体原因分析

1. **plan 阶段未生成 controlled_expansion_directives**
   - 03-plan prompt 要求在 assisted_expansion 模式下生成 `controlled_expansion_directives`
   - 但 plan.schema.json 中该字段为可选，模型未输出
   - draft 阶段因此没有扩写指令参考

2. **draft 阶段未输出 expansion_report**
   - 04-draft prompt 有详细扩写规则
   - 但模型只输出了 required 字段（draft_policy 等），跳过了 v0.1.4 新增字段
   - 没有 expansion_report，意味着模型可能根本没有进行扩写

3. **rewrite 阶段可能压缩了扩写**
   - 06-rewrite prompt 说"可接受扩写应保留"
   - 但如果 draft 本身就没有扩写，rewrite 自然也无从保留

4. **run_gray.py 纯文本输入缺少 expansion intent**
   - `generate_temp_input()` 的 requirement 固定为："请将以下素材整理成芒果系新闻稿，正式、有传播感，适合对外发布"
   - 这个 requirement 没有明确表达"请扩写"的意图
   - 模型可能将其理解为普通的新闻稿生成任务

5. **safe_official 和 assisted_expansion 共用相同 prompt 模板**
   - 两个模式使用同一个 `04-draft.md`
   - 区别仅在于 prompt 中的 `{{generation_mode}}` 变量
   - 模型对变量值的注意力可能不足

## 五、长稿超时原因

### 5.1 C1.9C Case C 超时分析

run_gray.py 的 timeout 设置为 **300 秒**。

assisted_expansion 模式下的调用链：
1. classify → 模型调用
2. extract → 模型调用
3. plan → 模型调用（prompt 变长，含 controlled_expansion_directives 指令）
4. draft → 模型调用（prompt 变长，含扩写规则 + RAG 检索）
5. review → 模型调用（prompt 变长，含 expansion_review 规则）
6. rewrite → 模型调用
7. quality_score → 模型调用（可能触发返修循环）
8. quality_rewrite_round_1 → rewrite 再次调用
9. quality_score_round_2 → 再次评估

**最多 9 次模型调用**（6 阶段 + 2 轮质量返修 × 2 次调用）。

### 5.2 超时原因判断

| 原因 | 是否成立 | 说明 |
|------|---------|------|
| 模型调用变慢 | ⚠️ 可能 | DeepSeek API 响应时间波动 |
| prompt 变长 | ✅ 成立 | assisted_expansion 的 prompt 包含更多指令，token 数增加 |
| 触发更多阶段 | ✅ 成立 | 质量门禁返修循环最多增加 4 次模型调用 |
| run_gray.py timeout 太短 | ✅ 成立 | 300s 对 9 次模型调用偏紧 |
| 长稿本身 token 多 | ✅ 成立 | 长稿输入 + 长稿输出 = 更长的模型处理时间 |

### 5.3 建议

- **不要避免 assisted_expansion 跑长稿**——问题不在模式本身
- **建议将 timeout 从 300s 调整为 480s**（8 分钟）
- **或在 run_gray.py 中支持 `--timeout` 参数**
- **长稿 + 质量返修 = 预期内的多次调用**，不应因此放弃该模式

## 六、发现的 Bug

### Bug #1：gray-record 字段名不匹配（低优先级）

**位置**：`scripts/run_gray.py` → `generate_gray_record()`

**问题**：
```python
has_expansion_report = "expansion_report" in report  # 应为 "expansion_report_summary"
has_expansion_review = "expansion_review" in report  # 应为 "expansion_review_summary"
```

**影响**：灰度记录始终显示 expansion_report/expansion_review 为 ❌，即使数据存在。

**修复**：改字段名检查为 `expansion_report_summary` / `expansion_review_summary`。

### Bug #2：draft_official 未定义变量引用（低优先级）

**位置**：`pipeline/run_pipeline.py` 第 702 行

**问题**：
```python
if report.official_use_allowed is None and draft_official is not None:
    report.official_use_allowed = draft_official
```

`draft_official` 从未定义。这段代码会抛 `NameError`。

**影响**：实际上不会触发，因为 `report.official_use_allowed` 在前面已经通过 `gen_flags` 设置了值（不会是 None）。但如果未来逻辑变化导致 `gen_flags` 未设置，这里会崩溃。

**修复**：改为 `draft_result.get("official_use_allowed")` 或删除这段 dead code。

### Bug #3：模型未输出 v0.1.4 新增字段（核心问题）

**位置**：DeepSeek 模型对 04-draft prompt 的响应

**问题**：模型没有输出 `generation_mode` / `expansion_report` / `official_use_allowed` / `draft_disclaimer` / `expansion_policy` 等 v0.1.4 新增字段。

**影响**：
- expansion_report 实际来自 pipeline fallback 而非模型
- 扩写行为可能根本没有发生
- assisted_expansion 模式名存实亡

## 八、结论

### 最终判断：**B. ⚠️ 链路部分断裂，需要最小修复**

- ✅ **数据传递链路完整**：generation_mode 从 CLI 参数到 prompt context 的传递完全正常

**assisted_expansion 当前可用性评估**：
- 模式可以运行，不会报错
- generation_mode 正确记录到 pipeline_report

**是否建议进入 C1.9E**：✅ 建议进入，但 C1.9E 应聚焦于：
1. 实施 P0 修复（让模型真正输出 expansion_report）
