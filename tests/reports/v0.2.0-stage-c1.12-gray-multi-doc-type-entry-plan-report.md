## 一、审计 run_gray.py 当前文体入口

### 1.1 粘贴文本时是否固定 specified_doc_type=新闻稿？

**✅ 是，硬编码。**

`generate_temp_input()` 函数中：
```python
input_data = {
    "requirement": _get_requirement_for_mode(mode),
    "draft": text,
    "specified_doc_type": "新闻稿",  # ← 硬编码
    "generation_mode": mode,
}
```

### 1.2 requirement 是否固定"整理成芒果系新闻稿"？

**✅ 是。** `_get_requirement_for_mode()` 三个分支都提到"新闻稿"：
- safe_official："请将以下素材整理成芒果系新闻稿，正式、有传播感，适合对外发布"
- assisted_expansion："请在不编造具体事实的前提下，对输入素材进行适度扩写和成稿化处理"（虽然没提"新闻稿"，但 specified_doc_type=新闻稿 会引导 classify 判定为新闻稿）
- creative_mimic："请将以下素材整理成芒果系风格稿件（内部灵感稿）"

### 1.3 --mode 是否只控制 generation_mode，不控制 doc_type？

**✅ 是。** `--mode` 参数只影响 `generation_mode`（safe_official / assisted_expansion / creative_mimic），不影响 `specified_doc_type`。

### 1.4 是否支持用户指定 doc_type？

**❌ 不支持。** `argparse` 只有 `--mode` 和 `--timeout` 参数，没有 `--doc-type`。

### 1.5 文件输入时是否保留原 input json doc_type？

**✅ 保留。** 文件输入时直接读取原 JSON，不覆盖 specified_doc_type。但粘贴文本时强制为新闻稿。

### 1.6 当前为什么 C1.11 全部变成新闻稿？

**根因链**：
1. run_gray.py 粘贴文本 → `specified_doc_type: "新闻稿"` 硬编码
2. classify 阶段收到 `specified_doc_type=新闻稿` → 判定为新闻稿
3. plan/draft/review/rewrite 全部按新闻稿规则执行
4. doc-type-rules.md 的"司情稿件补充约束"章节声明适用于"run_gray.py 灰度模式生成的稿件" → 所有灰度输出都受司情约束
5. 结果：所有灰度输出都被拉成"司情新闻稿"风格

## 二、审计 pipeline 多文体能力

### 2.1 系统当前支持哪些文体？

doc-type-rules.md 定义了 **10 种文种规则**：

| 文种 | 有独立规则 | RAG 路由 | rerank 权重 |
|------|-----------|---------|------------|
| 新闻稿 | ✅ | style 4 + business 2 | dianguang_media +1.0 |
| 通知 | ✅ | business 6 | 默认 |
| 请示 | ✅ | business 6 | 默认 |
| 报告 | ✅ | business 6 | 默认 |
| 函 | ✅ | business 6 | 默认 |
| 总结 | ✅ | business 5 + style 1 | 默认 |
| 汇报材料 | ✅ | business 5 + style 1 | hunan_mango +1.5 |
| 领导讲话 | ✅ | style 3 + business 3 | hunan_mango +2.0, leader_speech +1.0 |
| 会议纪要 | ✅ | business 6 | 默认 |
| 通报 | ✅ | business 5 + style 1 | 默认 |

### 2.2 哪些文体有独立 prompt / rule？

**所有 10 种文种**都在 doc-type-rules.md 中有独立章节，包含：
- 适用场景
- 行文方向
- 标题格式
- 正文结构
- 常用表达
- 禁忌

04-draft.md 中也有每种文种的独立生成规则。

### 2.3 RAG routing 对不同文体是否不同？

**✅ 是，差异显著。**

- **新闻稿/活动稿/宣传稿**：style 为主（4），business 为辅（2）
- **领导讲话**：style 3 + business 3，且 rerank 对 hunan_mango 加权 +2.0
- **汇报材料**：business 为主（5），style 为辅（1），rerank 对 hunan_mango 加权 +1.5
- **报告/请示/通知/函/会议纪要**：纯 business（6），不查 style
- **司情新闻稿**：与新闻稿相同路由

### 2.4 assisted_expansion 在不同文体下是否有差异化规则？

**⚠️ 部分有。**

04-draft.md 的 assisted_expansion 规则列出了通用扩写边界，但没有按文种细分。例如：
- 领导讲话应允许更强的"领导讲话句式风格"扩写
- 汇报材料应允许"工作导向表达"扩写
- 公文/通知应更克制，不允许宣传化扩写

当前这些差异依赖 classify 自动识别 + doc-type-rules.md 约束，但 assisted_expansion 的扩写规则本身没有按文种区分。

### 2.5 司情稿件补充约束是否影响所有灰度输出？

**⚠️ 是的，这是一个问题。**

doc-type-rules.md 末尾的"司情稿件补充约束（2026-06-02 新增）"声明：
> 以下约束适用于来源为「电广传媒司情」或「电广传媒《每周司情》」的新闻稿，**以及 run_gray.py 灰度模式生成的稿件**。

这意味着**所有 run_gray.py 输出**（无论什么文种）都受司情约束。这会导致：
- 领导讲话被拉成司情风格
- 汇报材料被拉成司情风格
- 公文/通知被拉成司情风格

**这是 C1.11 输出"统一成司情风"的另一个根因。**

## 三、多文体灰度入口设计

### 3.1 新增 --doc-type 参数

```
python scripts/run_gray.py --mode assisted_expansion --doc-type 新闻稿 "材料"
python scripts/run_gray.py --mode assisted_expansion --doc-type 领导讲话 "材料"
python scripts/run_gray.py --mode assisted_expansion --doc-type 汇报材料 "材料"
python scripts/run_gray.py --mode assisted_expansion --doc-type 通知 "材料"
python scripts/run_gray.py --mode assisted_expansion --doc-type auto "材料"
```

**默认值**：`新闻稿`（向后兼容）

**合法值**：`新闻稿 / 领导讲话 / 汇报材料 / 通知 / 请示 / 报告 / 函 / 总结 / 会议纪要 / 通报 / auto`

### 3.2 参数行为

| 场景 | specified_doc_type | requirement |
|------|-------------------|-------------|
| `--doc-type 新闻稿` | 新闻稿 | "请将以下素材整理成芒果系新闻稿…" |
| `--doc-type 领导讲话` | 领导讲话 | "请将以下素材整理成正式领导讲话稿…" |
| `--doc-type 汇报材料` | 汇报材料 | "请将以下素材整理成芒果系汇报材料…" |
| `--doc-type auto` | 不传（由 classify 自动判断） | "请将以下素材整理成正式文稿…" |
| 不传（默认） | 新闻稿 | 保持原行为 |

### 3.3 requirement 动态模板

```python
DOC_TYPE_REQUIREMENTS = {
    "新闻稿": "请将以下素材整理成芒果系新闻稿，正式、有传播感，适合对外发布",
    "领导讲话": "请将以下素材整理成正式领导讲话稿，体现政治站位和工作部署，语气庄重有力",
    "汇报材料": "请将以下素材整理成芒果系汇报材料，突出工作进展、亮点成效和下一步思路",
    "通知": "请将以下素材整理成正式通知，语言直接、清楚，明确对象、事项、时间、要求",
    "请示": "请将以下素材整理成正式请示，一文一事，结尾使用妥否请批示",
    "报告": "请将以下素材整理成正式报告，汇报情况，不得夹带请示事项",
    "会议纪要": "请将以下素材整理成正式会议纪要，记录会议事项、议定事项、责任分工",
    "总结": "请将以下素材整理成工作总结，包含工作开展情况、主要成效、经验做法、存在问题、下一步计划",
    "函": "请将以下素材整理成正式函，语气平实，面向平级或不相隶属单位",
    "通报": "请将以下素材整理成正式通报，事实准确，不得夸大",
    "auto": "请将以下素材整理成正式文稿，根据内容自动匹配合适文种",
}
```

### 3.4 gray-record 新增字段

gray-record 新增 `doc_type_source` 字段：
- `user_specified`：用户通过 `--doc-type` 指定
- `input_file`：从输入 JSON 文件中读取
- `auto`：classify 自动判断（`--doc-type auto`）
- `default`：默认值（新闻稿）

### 3.5 司情约束范围修正

建议将"司情稿件补充约束"的适用范围修改为：
- ✅ 适用于：来源为「电广传媒司情」的新闻稿
- ✅ 适用于：`--doc-type 司情新闻稿` 的灰度输出
- ❌ 不适用于：领导讲话、汇报材料、公文等非司情文种

## 六、风险和回滚

| 风险 | 说明 | 缓解 |
|------|------|------|
| 文种识别错误 | `--doc-type auto` 时 classify 可能判错 | auto 模式下 gray-record 记录 classify 结果，人工可复核 |
| 司情约束误用 | 修改 doc-type-rules.md 可能影响其他逻辑 | 只修改适用范围声明，不改规则内容 |
| 向后兼容 | 新参数可能破坏已有脚本 | 默认值=新闻稿，不传参时行为不变 |

**回滚方案**：删除 `--doc-type` 参数，恢复硬编码新闻稿。
