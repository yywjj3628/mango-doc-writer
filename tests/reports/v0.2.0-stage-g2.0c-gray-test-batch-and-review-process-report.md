## 一、批次节奏

### 第一轮：8-12 case

| 维度 | 建议 |
|------|------|
| 总量 | 8-12 篇 |
| 批次数 | 2-3 批 |
| 每批数量 | 4 篇（如单篇耗时过长，降为 2 篇） |
| 批次间隔 | 用户评分完成后启动下一批 |
| 并发 | 不并发，串行执行 |
| 风格覆盖 | 每批覆盖不同 style_domain / output_doc_type |

**推荐批次分配：**

| 批次 | 矩阵编号 | style_domain | 文种 |
|------|---------|-------------|------|
| 第 1 批 | M-01, M-02, M-03, M-04 | dianguang_siqing | 新闻稿×2, 会议新闻, 亮点工作材料 |
| 第 2 批 | M-05, M-06, M-07, M-08a | mixed | 宣传推文, 工作方案, 汇报材料, 会议新闻 |
| 第 3 批（可选） | M-08b, 补测 | mixed | 会议纪要, 补测第一轮问题方向 |

### 第二轮：补足到 20 篇

| 维度 | 建议 |
|------|------|
| 目标 | 累计 20 篇，真实素材 ≥ 8 篇，文种覆盖 ≥ 6 类 |
| 重点 | 针对第一轮暴露问题补测 |
| 批次 | 2-3 批 |
| 每批 | 4 篇 |

## 二、每批测试流程

```
1. 用户提供素材（或指定使用旧司情最小事实化素材）
   ↓
2. OpenClaw 标注矩阵编号 M-xx
   ↓
3. OpenClaw 明确五字段：
   - style_domain
   - organization_scope
   - content_type
   - output_doc_type
   - length_mode
   ↓
4. OpenClaw 使用 run_gray.py 灰度模式执行
   ↓
5. 每篇生成单独 gray-record
   ↓
6. 批次完成后输出：
   - final_markdown 汇总
   - 每篇 QG / RAG / 文种 / 主体检查
   - 人工评分表
   ↓
7. 用户人工评分
   ↓
8. OpenClaw 写入 gray usage ledger
```

## 三、人工评分模板

### 模板 A：单篇简短反馈

```
这篇[修改后采用]，风格[4]分。文种[对]，主体[对]，事实[安全]。
主要问题：[结尾偏空，第二段略短]。请记入灰度使用台账。
```

**示例：**
```
这篇修改后采用，风格4分。文种对，主体对，事实安全。主要问题：结尾偏空，第二段略短。请记入灰度使用台账。
```

### 模板 B：批量反馈表

```
Case 1：[修改后采用] / 风格[4] / 文种[对] / 主体[对] / 事实[安全] / 问题：[结尾偏空]
Case 2：[弃用] / 风格[2] / 文种[错] / 主体[对] / 事实[安全] / 问题：[写成汇报材料]
Case 3：[直接采用] / 风格[5] / 文种[对] / 主体[对] / 事实[安全] / 问题：[无]
Case 4：[修改后采用] / 风格[3] / 文种[对] / 主体[对] / 事实[安全] / 问题：[扩写不足]
```

### 模板 C：极简反馈

```
Case 1：7分，修改后采用，事实安全，问题是偏短。
Case 2：5分，弃用，文种错，写成汇报材料了。
```

## 四、台账记录规则

### 主台账

**位置**：`tests/reports/gray-usage/gray-usage-ledger.md`

**记录内容**：
- case_id（G-xxx）
- 矩阵编号（M-xx）
- 素材来源类型（真实新素材 / 旧司情最小事实化 / 历史事实改写）
- 五字段
- requested_doc_type
- classified_doc_type
- RAG primary
- QG 结果
- final_markdown 路径
- 人工评价（6 项）
- 是否采用
- 主要问题
- 是否触发立即修复

### 单篇记录

**位置**：`tests/reports/gray-usage/gray-record-YYYYMMDD_HHMMSS.md`

**自动由 run_gray.py 生成**，无需手动创建。

## 五、问题归类规则

每 10 篇归类一次：

| 类别 | 问题类型 | 修复方向 |
|------|---------|---------|
| A 类 | 主体/组织称谓问题 | 修 org-title-dictionary.yaml |
| B 类 | 文种结构问题 | 修 doc-type-rules.md |
| C 类 | 风格问题 | 调 RAG/rerank 或 style rules |
| D 类 | 事实扩写问题 | 修 expansion policy / prompt |
| E 类 | 篇幅问题 | 调 length rules / prompt |
| F 类 | 输入格式问题 | 修 run_gray/input_parser 使用方式 |

## 六、修复触发规则

### 立即修复（不能等 10 篇归类）

| 触发条件 | 说明 |
|---------|------|
| 事实风险 | 编造数据、虚构领导评价、捏造获奖信息 |
| 主体混用 | 电广传媒/芒果超媒混淆、子公司写成母公司 |
| 领导职务编造 | 编造不存在的职务、职务与实际不符 |
| 严重文种误判 | 会议新闻写成会议纪要、新闻稿写成汇报材料 |
| 禁用组织口径 | "公司"误指子公司、泛化组织名 |
| RAG 错库污染 | 错误 collection 语料混入，风格完全不对 |

### 累计触发（出现 2-3 次后修复）

| 触发条件 | 说明 |
|---------|------|
| 同类问题出现 2-3 次 | 某类问题反复出现 |
| 同一文种连续表现差 | 某文种多次评分低 |
| 某 style_domain 风格评分连续低于 3 | 风格持续偏差 |
| 可用性连续弃用 | 连续 2-3 篇弃用 |

### 不立即修（记录即可）

| 情况 | 说明 |
|------|------|
| 单篇偏短 | length_mode 或素材不足导致 |
| 单篇结尾偏空 | 模型生成习惯 |
| 单篇表达不够亮 | 风格细节 |
| 输入素材明显不足导致质量一般 | 非系统问题 |
