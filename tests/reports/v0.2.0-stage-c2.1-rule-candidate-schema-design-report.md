## 四、新增文种规则候选

### 4.1 亮点工作材料

- **结构**：背景 → 主要亮点 → 具体举措 → 阶段成效 → 经验启示 → 下一步计划
- **语调**：正式、务实、有数据支撑，突出创新和成效
- **必须元素**：标题、至少3个亮点、数据支撑、阶段成效
- **禁止元素**：流水账式罗列、空洞口号、无数据支撑的成果
- **篇幅**：600-900字（司情），1000-1500字（集团级）

### 4.2 宣传推文

- **结构**：传播性标题 → 活动导语 → 现场/亮点 → 主体价值 → 意义提升 → 行动/展望
- **语调**：活泼、有传播力，兼顾正式与生动
- **必须元素**：传播性标题、活动/事件核心、价值提炼
- **禁止元素**：纯公文语调、无传播点的平铺直叙、过长段落
- **篇幅**：800-1200字（公众号推文）

### 4.3 工作方案

- **结构**：背景依据 → 总体目标 → 重点任务 → 责任分工 → 时间安排 → 保障措施
- **语调**：严谨、可操作，强调责任和时间节点
- **必须元素**：背景依据、总体目标、重点任务、责任分工、时间安排
- **禁止元素**：空泛目标、无责任人的任务、无时间节点的安排
- **篇幅**：1500-3000字

## 六、正式规则合并原则

### 6.1 核心原则

1. **C2 阶段只生成 candidates，不自动修改正式 references**
   - 所有候选先写入 `tests/reports/rule-candidates/`
   - 人工确认后才可合并

2. **领导职务、组织归属、公司简称必须人工确认后才能合并**
   - 这三类信息直接影响生成质量
   - 历史语料不能直接视为最新事实

3. **历史语料不能直接视为最新事实**
   - 旧稿中的领导职务可能已变动
   - 组织架构可能已调整
   - 必须确认时效性

4. **style_phrase / doc_type_rule 可以由 AI 提炼，但仍需人工确认**
   - AI 可以从语料中总结模式
   - 但最终规则需要人工把关

5. **field_hint_rule 后续可用于迁出 run_gray.py 硬编码 hints**
   - 本阶段只设计 schema，不迁出
   - C2.3 确认后才迁出到 `references/rules/`

6. **合并正式规则时必须保留来源、确认日期、确认人或 reviewer_note**
   - 确保可追溯
   - 便于后续更新

### 6.2 合并流程

```
候选 JSONL (c2.2)
  ↓ 人工确认
审核结果 (c2.3)
  ↓ 过滤 apply_to_formal_rules=true
合并脚本
  ↓ 写入正式规则库
references/rules/
```

## 七、人工确认模板说明

### 7.1 确认方式

**推荐使用 CSV 模板**：
1. 用 Excel 打开 `c2.1-human-review-template.csv`
2. 逐行审核，填写 `reviewer_decision`、`corrected_value`、`apply_to_formal_rules`
3. 保存后回写到 JSONL 文件

### 7.2 审核决定

| 决定 | 含义 | 后续动作 |
|------|------|---------|
| ✅ approved | 直接采用 | apply_to_formal_rules=true |
| ✏️ modified | 修改后采用 | corrected_value 填写正确值 |
| ❌ rejected | 弃用 | apply_to_formal_rules=false |
| ⏸️ deferred | 暂缓 | 保留待后续处理 |

### 7.3 审核要点

| 候选类型 | 重点检查 |
|---------|---------|
| leader_title | 姓名、职务、组织是否正确，是否有时效性 |
| subsidiary_affiliation | 归属关系是否准确，关系类型是否合适 |
| company_alias | 全称/简称是否正确，适用/禁用场景 |
| doc_type_rule | 结构是否合理，必须/禁止元素是否准确 |
| style_phrase | 表达是否准确，使用场景是否合适 |
| risk_rule | 风险类型是否准确，安全替代是否可行 |
| field_hint_rule | 字段名/值是否正确，提示文本是否清晰 |
