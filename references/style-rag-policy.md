# style-rag-policy.md
# RAG 风格参考策略
# 本文件定义 RAG 在 mango-doc-writer 中的定位、调用时机、输入输出边界和风险控制。

---

## 一、style_rag 的定位

style_rag 是**风格案例检索层**。

### 可以用于

| 用途 | 说明 | 示例 |
|------|------|------|
| 芒果系文风参考 | 借鉴整体表达风格 | 长句为主、排比结构、战略词密集 |
| 标题风格参考 | 借鉴标题表达方式 | 对仗式、成果倒叙式、战略定位式 |
| 开头句式参考 | 借鉴首段展开方式 | 时间+事件+人物+核心动作 |
| 段落节奏参考 | 借鉴段落长度和句式节奏 | 概述段80-150字、主体段150-300字 |
| 战略表达参考 | 借鉴战略词用法 | 五新战略、双前锋、系统性变革 |
| 同类文种案例参考 | 同一文种的历史成稿风格 | 参考新闻稿结构、报告格式 |
| 稳定表达模式参考 | 高频稳定出现的表达 | 开头模板、结尾模板、过渡句 |
| 文体风格参考 | 不同场景的风格差异 | 新闻稿风格3、通知风格1 |

### 不可用于

| 禁止用途 | 原因 |
|----------|------|
| 决定文种 | 由 classify 阶段负责，基于 doc-type-rules.md |
| 决定主送单位 | 由文种规则和用户提供信息决定 |
| 决定领导职务 | 由 org-title-dictionary.yaml 负责 |
| 决定机构全称 | 由 org-title-dictionary.yaml 负责 |
| 自动补充当次事实 | 只能使用用户提供的素材 |
| 自动补充当次数据 | 只能使用用户提供的素材 |
| 自动补充领导出席 | 只能使用用户提供的素材 |
| 自动补充领导评价 | 只能使用用户提供的素材 |
| 自动补充获奖信息 | 只能使用用户提供的素材 |
| 判断公文禁忌 | 由 doc-type-rules.md 负责 |

## 二、RAG 与三类知识库的关系

### 三类知识分层

| 层 | 名称 | 来源 | 职责 | 优先级 |
|----|------|------|------|--------|
| 1 | rules_db | doc-type-rules.md | 决定**能不能这么写** | 最高 |
| 2 | facts_db | org-title-dictionary.yaml | 决定**应该怎么称呼** | 高 |
| 3 | style_rag | 60篇旧稿 / style-guide / RAG语料 | 决定**写得像不像芒果系** | 低（参考） |

### 优先级规则

1. **文种规则**以 `doc-type-rules.md` 为准。
2. **机构称谓、领导职务、产品名称、战略口径**以 `org-title-dictionary.yaml` 为准。
3. **RAG 只提供表达参考**，不作为事实或称谓的权威来源。
4. RAG 与称谓库冲突时，以 `org-title-dictionary.yaml` 为准。
5. RAG 与文种规则冲突时，以 `doc-type-rules.md` 为准。
6. RAG 与用户当次明确输入冲突时，优先保留用户输入并提示冲突。

## 三、RAG 调用时机

### 正确调用顺序

```
classify（识别文种）
  → extract（抽取事实字段）
    → load doc-type-rules（加载文种规则）
      → load org-title-dictionary（加载称谓口径）
        → retrieve style_rag（检索风格参考）
          → plan（生成结构提纲）
            → draft（生成初稿）
              → review（质检）
                → rewrite（二次修订）
```

### 核心规则

- **RAG 不在流程第一步调用。**
- 必须先完成 classify（识别文种），再根据文种和场景生成 RAG 检索 query。
- 必须先完成 extract（事实抽取），明确用户提供了哪些素材，才能区分 RAG 结果中哪些是可借鉴的表达、哪些是不能照抄的事实。
- 必须先加载 doc-type-rules 和 org-title-dictionary，建立文种约束和称谓约束，才能在 RAG 结果整理时正确执行 `reference_phrases` 与 `do_not_copy` 的分离。

## 四、RAG 检索 query 生成规则

### 规则

1. query 根据文种 + 用户提供的关键词组合生成。
2. query 侧重表达风格，不侧重具体事实。
3. 每个 query 通常包含：文种类型 + 芒果系/广电 + 风格关键词。
4. 可根据用户素材中的主题词补充 query。

### 各文种 query 模板

#### 1. 新闻稿

```
query_1: "芒果系 新闻稿 活动 通稿 标题 开头"
query_2: "芒果日志 重大活动 文化科技 融合创新"
query_3: "广电 芒果 重大活动 新闻稿 传播表达"
```

- 使用场景：对外宣传通稿、活动发布、成果展示。
- 侧重：标题风格、开头句式、战略表达、结尾升华。

#### 2. 请示

```
query_1: "广电系统 请示 项目支持 上行文"
query_2: "正式公文 请示 妥否请批示"
query_3: "请示 事项 理由 必要性 可行性"
```

- 使用场景：向上级请求批准。
- 侧重：上行文语气、请示结构、论证逻辑、结尾用语。

#### 3. 报告

```
query_1: "广电系统 汇报材料 工作报告 经营情况 下一步工作"
query_2: "芒果系 报告 工作成效 存在问题 下一步"
query_3: "上行文 报告 正式表达"
```

- 使用场景：向上级汇报工作进展、专项工作完成情况。
- 侧重：报告结构（基本情况→主要成效→存在问题→下一步计划）、上行文语气。

#### 4. 通知

```
query_1: "广电系统 通知 布置工作 下行文"
query_2: "正式公文 通知 工作部署 时间要求"
query_3: "通知 转发 传达 贯彻落实"
```

- 使用场景：向下级布置工作、传达事项。
- 侧重：通知格式、分条列项、时间节点明确性。
- 注意：通知风格强度为1（克制正式），RAG 参考价值较低，以 doc-type-rules.md 为主。

#### 5. 汇报材料

```
query_1: "广电系统 汇报 经营情况 专题汇报"
query_2: "芒果系 汇报材料 数据支撑 问题困难"
query_3: "上行汇报 经营分析 工作成效"
```

- 使用场景：向上级或领导当面汇报的书面材料。
- 侧重：精炼表达、数据呈现方式、问题表述分寸。

#### 6. 领导讲话

```
query_1: "芒果系 领导讲话 站位 判断 部署 要求"
query_2: "广电系统 讲话稿 政治站位 工作部署"
query_3: "文化科技融合 领导讲话 芒果表达"
```

- 使用场景：领导在会议、活动上的讲话稿。
- 侧重：站位段表达、形势判断、工作部署句式、号召结尾。

#### 7. 总结

```
query_1: "广电系统 总结 年度总结 工作成效 存在问题"
query_2: "芒果系 总结 复盘 经验教训 改进措施"
query_3: "工作总结 成绩 不足 下一步计划"
```

- 使用场景：阶段性工作复盘、年度/季度总结。
- 侧重：成绩总结句式、问题表述、经验提炼方式。

#### 8. 会议纪要

```
query_1: "广电系统 会议纪要 议定事项 责任分工"
query_2: "正式公文 会议纪要 客观记录"
```

- 使用场景：记录会议议定事项和责任分工。
- 侧重：纪要格式、客观记录语气、议定事项表述。
- 注意：会议纪要风格强度为1（克制正式），RAG 参考价值较低，以 doc-type-rules.md 为主。

## 五、召回数量控制

### 配置建议

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| top_k（默认） | 3 | 默认召回3条风格参考 |
| max_top_k（最大） | 5 | 最多召回5条，不超过 |
| chunk_size | 600-1000 字符 | 单个召回片段的长度范围 |
| rerank | optional | 可选，按相关度重排序 |

### 规则

1. **默认召回 3 条**，足够提供风格参考，不至于信息过载。
2. **最多召回 5 条**，仅在需要更多同类文种对比时使用。
3. **不要一次性召回过多旧稿**——召回越多，`do_not_copy` 筛选工作量越大，照抄事实的风险越高。
4. **召回结果要先整理**为 `style_references` 格式，再进入 draft 阶段。
5. **不允许把 RAG 原文整段塞入最终稿**——只借鉴表达方式，不照抄内容。

## 六、RAG 结果整理格式

RAG 检索结果在进入 draft 阶段前，必须整理为以下结构化格式：

```yaml
style_references:
  - source: "旧稿标题 / 来源名称"
    doc_type: "新闻稿 / 报告 / 讲话稿 / 等"
    relevance_score: 0.75
    use_for:
      - "标题风格"
      - "开头句式"
      - "段落节奏"
      - "战略表达"
    reference_phrases:
      - "可借鉴的短语或句式（仅表达，不含事实）"
      - "例如：以五新战略为牵引接续奋斗"
      - "例如：从工具应用到智媒跃升"
    structure_patterns:
      - "可借鉴的段落结构（仅骨架，不含具体内容）"
      - "例如：概述段→背景段→主体段→数据段→结尾段"
    do_not_copy:
      - "具体数据（如：会员达7560万）"
      - "当次时间（如：5月22日）"
      - "当次地点（如：在深圳）"
      - "领导出席信息"
      - "领导评价"
      - "项目成果"
      - "获奖信息"
    risk_notes:
      - "本条涉及XX活动报道，其中的活动数据不得迁移到新稿"
      - "本条涉及领导讲话，其中的讲话内容不得作为新稿领导评价"
```

### 整理规则

1. 每条 RAG 结果必须明确区分 `reference_phrases`（可借鉴）和 `do_not_copy`（不可照抄）。
2. `reference_phrases` 只提取表达模式，不包含具体事实。
3. `do_not_copy` 必须列出本条中所有与当次事实相关的内容。
4. `risk_notes` 提醒哪些内容存在误用风险。
5. 整理后的 `style_references` 总量控制在 10-20 个可借鉴短语，不超过 30 个。

## 七、reference_phrases 与 do_not_copy 分离逻辑

### reference_phrases 可以提供

| 类型 | 示例 | 来源 |
|------|------|------|
| 标题表达 | "以变求新，向新而生" | 旧稿标题 |
| 开头句式 | "[日期]，[事件]在[地点]举行" | 旧稿开头模板 |
| 过渡句 | "在……的推动下"、"通过……的深度融合" | doc-type-rules.md |
| 战略表达 | "锚定数智化平台型媒体集团总体目标" | style-guide |
| 总结性表达 | "逆风而行、顶压作战完成年度目标" | 旧稿 |
| 芒果系常用修辞 | "双前锋"、"水电煤"、"行业地貌" | style-guide |
| 段落组织方式 | "破折号排比——XX、XX、XX" | 旧稿句式 |

### do_not_copy 必须拦截

| 拦截类型 | 示例 | 原因 |
|----------|------|------|
| 旧稿中的具体时间 | "5月22日" | 当次事件时间，非新稿事件时间 |
| 旧稿中的具体地点 | "在深圳"、"在马栏山" | 当次事件地点，非新稿事件地点 |
| 旧稿中的具体领导出席 | "龚政文出席并讲话" | 当次出席情况，非新稿出席情况 |
| 旧稿中的具体评价 | "领导高度肯定" | 当次评价，非新稿评价 |
| 旧稿中的具体数据 | "会员达7560万" | 当次数据，非新稿数据 |
| 旧稿中的具体成果 | "第七次获此殊荣" | 当次成果，非新稿成果 |
| 旧稿中的具体奖项 | "全国文化企业30强" | 当次奖项，非新稿奖项 |
| 旧稿中的具体项目细节 | "三湘星光行动第九颗星" | 当次项目，非新稿项目 |

### 分离判断标准

**问自己：这个信息是"怎么说的"还是"说了什么"？**

- "怎么说的" → `reference_phrases`（句式、结构、表达风格）
- "说了什么" → `do_not_copy`（事实、数据、具体内容）

## 八、旧稿继承与 RAG 引用边界

### 可以通过 org-title-dictionary.yaml 继承的稳定口径

| 可继承内容 | 示例 | 进入位置 |
|-----------|------|---------|
| 机构名称 | "湖南广播影视集团（台）" | organizations |
| 领导职务 | "龚政文：集团（台）党委书记、董事长" | leaders |
| 产品名称 | "芒果TV"、"金种子计划" | products |
| 战略表达 | "五新战略"、"双前锋" | strategic_terms |
| 固定搭配 | "锚定……总体目标" | fixed_replacements |
| 常用称谓 | "集团（台）" | organizations.aliases |

> 上述内容已在阶段 3 的 org-title-dictionary.yaml 中建立，不在 RAG 实时检索流程中处理。

### 不得通过 RAG 直接进入新稿的当次事实

| 禁止迁移内容 | 原因 |
|-------------|------|
| 某次会议时间 | 时间属于当次事实，必须来自用户素材 |
| 某次活动地点 | 地点属于当次事实，必须来自用户素材 |
| 某次领导出席 | 出席属于当次事实，必须来自用户素材 |
| 某次讲话评价 | 评价属于当次事实，必须来自用户素材 |
| 某次经营数据 | 数据属于当次事实，必须来自用户素材 |
| 某次成果表述 | 成果属于当次事实，必须来自用户素材 |
| 某次获奖信息 | 奖项属于当次事实，必须来自用户素材 |

## 九、冲突处理规则

### 1. RAG 与 doc-type-rules.md 冲突

- **以 doc-type-rules.md 为准**。
- RAG 中的表达若违反文种规则（如通知中出现宣传表达），不采用。
- 标记：`【style_rag 表达与 doc-type-rules 冲突，已忽略 RAG 表达】`。

### 2. RAG 与 org-title-dictionary.yaml 冲突

- **以 org-title-dictionary.yaml 为准**。
- RAG 中出现的领导职务/机构名称若与本库不一致，以本库为准。
- 例如：RAG 旧稿中写"龚政文说"，但本库要求"龚政文指出/表示/强调"，则以本库为准。
- 标记：`【style_rag 称谓与 org-title-dictionary 冲突，已以口径库为准】`。

### 3. RAG 与用户当次输入冲突

- **优先使用用户当次输入**。
- 同时标记冲突，建议人工确认。
- 例如：用户本次指定领导职务为"XXX总经理"，但 RAG 旧稿中该领导职务不同，使用用户指定，标记：`【用户输入与历史口径不一致，建议人工确认】`。

### 4. 多条 RAG 结果互相冲突

- **不自动选择**。
- 标记为：`【历史样稿口径不一致】`。
- 将冲突内容列出，供 draft 阶段参考但不得自动采用。

### 5. RAG 检索不到结果

- **不阻塞生成流程**。
- 使用 doc-type-rules.md + org-title-dictionary.yaml + 用户素材 + style-guide.md 继续生成。
- 标记：`【本次未获得 RAG 风格参考】`。
- 此时不影响稿件质量，因 doc-type-rules 和 org-title-dictionary 已覆盖核心约束，style-guide 也提供了表达模板。

## 十、风险控制清单

### 检索前

- [ ] 是否已完成 classify？
- [ ] 是否已完成 extract？
- [ ] 是否已加载 doc-type-rules？
- [ ] 是否已加载 org-title-dictionary？
- [ ] query 是否基于文种 + 风格关键词生成（而非事实关键词）？

### 检索后

- [ ] 召回数量是否在 3-5 条范围内？
- [ ] 是否已按 relevance_score 排序？
- [ ] 是否已整理为 style_references 格式？

### 整理时

- [ ] reference_phrases 是否仅包含表达模式（不含事实）？
- [ ] do_not_copy 是否列出了所有当次事实类内容？
- [ ] 是否标注了 risk_notes？

### 进入 draft 前

- [ ] 是否确认 reference_phrases 不与 doc-type-rules 冲突？
- [ ] 是否确认 reference_phrases 不与 org-title-dictionary 冲突？
- [ ] 是否确认不把 RAG 原文整段塞入稿件？

## 十一、RAG 服务配置

### 服务端点

- **地址**：`http://localhost:8000/search`
- **方法**：POST
- **Content-Type**：application/json
- **Collection**：`hunan_mango`

### 请求格式

```json
{
  "question": "<检索query>",
  "collection": "hunan_mango",
  "top_k": 3
}
```

### 响应处理

```python
# 伪代码示意
response = rag_search(question=query, collection="hunan_mango", top_k=3)
style_refs = []
for match in response.matches:
    ref = extract_style_reference(match)  # 提取表达模式
    do_not = extract_facts(match)          # 提取需要拦截的事实
    style_refs.append({
        "source": match.metadata.filename,
        "reference_phrases": ref,
        "do_not_copy": do_not
    })
```

## 十二、与 mango-writer 的关系

本 policy 与 mango-writer 的 RAG 使用有以下区别：

| 维度 | mango-writer | mango-doc-writer |
|------|-------------|------------------|
| 定位 | 核心依赖，两阶段管线必须 | 风格参考层，可选 |
| 调用时机 | stylize 阶段直接调用 | classify + extract 之后调用 |
| 结果处理 | 直接作为 prompt 上下文 | 必须整理为 style_references |
| 事实处理 | 整篇旧稿作为参考 | 严格区分 reference_phrases 和 do_not_copy |
| 文种感知 | 不区分文种 | 根据文种生成不同 query |

> mango-writer 保留不动。本 Skill 的 style_rag 策略在其基础上增加了文种感知、事实拦截和结构化整理。
